## Короткі результати дослідження

WCAG має чотири принципи: вміст можна сприйняти, ним можна керувати, він зрозумілий і правильно працює з допоміжними технологіями. Критерій успіху — конкретна перевірювана вимога. A, AA та AAA — рівні вимог; високий бал Lighthouse не доводить повної відповідності AA.

Для AA контраст звичайного тексту має бути щонайменше 4,5:1, великого — 3:1 (від 24 px або приблизно 18,66 px жирного). Значущі межі й стани елементів — 3:1. Цілі вказівника — 24 × 24 CSS px з винятками, зокрема для достатнього проміжку та посилань у тексті.

У WCAG 2.2 додано, зокрема, 2.4.11 (фокус не закритий), 2.5.7 (альтернатива перетягуванню), 2.5.8 (розмір цілі), 3.2.6 (послідовна допомога), 3.3.7 (не вводити те саме повторно), 3.3.8 (доступний вхід). 4.1.1 Parsing вилучено; перевірка HTML усе одно корисна.

Accessibility Tree показує зміст сторінки для допоміжних технологій: роль, назву, стан і зв’язки. DOM містить також декоративні та приховані вузли. Tab перевіряє фактичний порядок фокуса; Source Order Viewer допомагає зіставити порядок DOM із розташуванням на екрані.

В axe `violations` — знайдені порушення, `passes` — пройдені правила, `incomplete` — потрібна додаткова перевірка. Lighthouse Accessibility також використовує axe: це не два незалежні підтвердження. Інструмент не розуміє правдивість ціни, намір клікабельного `div` чи відповідність видимого FAQ його стану ARIA.

JSON-LD описує фактичний контент. `@context` задає словник, `@type` — тип сутності. Schema Markup Validator перевіряє словник Schema.org, Rich Results Test — підтримувані Google розширені результати. Валідна розмітка не гарантує розширеного результату. Для навчального FlowTask не можна вигадувати рейтинг.

Open Graph задає заголовок, опис, картинку, тип і URL картки поширення. `canonical` та `og:url` узгоджені для кожної сторінки. `robots.txt` регулює завантаження crawler, а `noindex` — індексацію; заборона crawling не гарантує видалення з пошуку. Sitemap перелічує абсолютні канонічні URL; вигаданий `lastmod` не потрібен.

LCP — час появи найбільшого видимого контенту, INP — реакція на взаємодії, CLS — небажані зсуви. Польові пороги на 75-му перцентилі: LCP ≤ 2,5 с, INP ≤ 200 мс, CLS ≤ 0,1. Звичайний Lighthouse navigation не вимірює INP. TBT стосується завантаження; затримку кліку тут перевірено окремою трасою, вона не названа польовим INP.

## Перевірка рекомендацій

Рішення нижче перевірені агентом; студент має повторити показані експерименти перед захистом.

1. **Прийнято:** замінити клікабельні div нативними елементами. Tab пропускає їх. Для переходу використано a; для надсилання форми button. WAI пояснює, що роль сама не додає клавіатурної поведінки [1].
2. **Відхилено:** альтернативне виправлення «достатньо додати role=button до div». Це змінить роль, але не реалізує Enter, Space та фокус. Нативний HTML простіший [1]. Це відхилений варіант AI, а не заява про виконану студентом перевірку.
3. **Прийнято:** синхронізувати aria-expanded FAQ. Підтвердження: DOM показує true при display:none; axe не повідомляє суперечність. Правило стану і зв’язок aria-controls описані WAI APG [2].
4. **Прийнято:** додати label до полів. Placeholder не є постійним видимим підписом, навіть коли браузер використовує його як запасну доступну назву. label зв’язано через for/id [3].
5. **Прийнято:** прибрати непідтверджений рейтинг і виправити ціну Pro на 29. Порівняно JSON-LD із видимим Pricing. Google вимагає правдивих даних, що представляють контент [4].
6. **Прийнято:** перенести промоблок у HTML і задати розміри hero. Lighthouse знайшов зсуви; код підтвердив пізню вставку. web.dev рекомендує резервувати місце та не вставляти контент над наявним [5].
7. **Прийнято:** оптимізувати hero без lazy-loading. Це потенційний LCP-ресурс, який потрібен одразу; затримувати його завантаження недоцільно [6].
8. **Залишено без зміни:** порожні alt аватарів. Імена вже написані поряд, тому повторювати їх у декоративних портретах не потрібно [7].
9. **Прийнято:** дозволити CSS і картинки у robots. Вони потрібні crawler для рендерингу. robots керує обходом, не є захистом приватних даних [8].

Окремий desktop axe: 6 типів порушень, 25 входжень елементів у правилах, 0 incomplete. Це не обов’язково 25 унікальних DOM-вузлів. На mobile Lighthouse також повідомляє target-size; відмінність пояснюється viewport і контекстом запуску.

Для двох автоматичних проблем додаткова перевірка DOM підтвердила відсутній alt hero та h4 після h1. Перед здачею потрібна особиста демонстрація цих елементів у DevTools.
